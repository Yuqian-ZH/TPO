# Deviations and reproducibility limits

| Item | Actual setting / reason |
|---|---|
| Policy size | `allenai/Llama-3.1-Tulu-3-8B-SFT`, rather than the paper's main 70B-SFT benchmark. No direct 8B-policy AlpacaEval table is reported in the published paper. |
| Benchmark size | Fixed 100/805 AlpacaEval-2 prompts, slice seed 42; exact original indices in `data/slice_ids.json`. Same reference outputs and instructions for all five stages. |
| Hardware | H100 80 GB GPU 2 for vLLM policy, GPU 3 for FsfairX RM. The two experiment runs are complete and the policy was stopped after Phase 1. |
| Context and output limits | vLLM `--max-model-len 16384` accommodates critique/update inputs plus the requested output limit. Candidate responses are capped at 2048 tokens; critique/gradient calls at 8192. Server context length and generated-token cap are different quantities. |
| Packaging fix | TextGrad `setup.py` references an undefined `readme`; changed `long_description` to an empty string before editable install. |
| Outlines import fix | The installed `pyairports==0.0.1` had no importable module. Installed original NICTA/pyairports 2.1.1 from commit `9699eae8c6b03c97239018dea92e01daa8594936`. This repaired vLLM generation without changing the model or optimizer. |
| Existing source changes | Before finishing, the repository already had edits to `run.py`, the TextGrad vLLM engine, `setup.py`, and README. These are preserved in `tpo_existing_changes.patch`. In particular, `max_token` was corrected to `max_tokens` and default caps changed to 2048. Both runs explicitly used `--max_tokens_all 8192`, so the runtime cap was 8192. No official TPO logic was changed during the finishing phases; hashes are checked against `official_logic_before_finish.sha256.json`. |
| Clean setup behavior | `setup_env.sh` retains official inference/optimizer code, with only the requested packaging fix. Official code's original 8192 engine default gives the same cap for the explicit 8192 run configuration. The historical patch is preserved as provenance, not automatically applied to current source. The setup script was syntax checked; a fresh-machine install was not executed on this occupied host. |
| Best-of-15 control | 15 initial response samples per prompt, seed 7, same sampling temperature/top_p and RM. This matches the requested response-candidate budget (5+5+5), not total FLOPs: TPO also generates textual critiques and gradients. 14 prompts have fewer than 15 stored answers due to duplicate merging. |
| Stored candidate counts | Initial/iter1/iter2 retain 492/419/414 answers, out of 500 requested each. Initial deficit 8 is duplicate merging. For refinements, missing response tags and duplicate merging are not separately identifiable because raw multi-sample optimizer responses were not logged. Combined deficits are 81 and 86, with component bounds in `robustness.json`. No missing historical counts were invented or rerun. |
| Judge | User-fixed `qwen3.8-max` via the configured DashScope-compatible Chat Completions endpoint; not the official GPT-4 Turbo judge. The endpoint response model field exposes the same alias, with no dated snapshot. Absolute scores are not leaderboard/paper comparable. |
| Annotator | `weighted_qwen3_8_max`, copied from AlpacaEval 0.6.6 `weighted_alpaca_eval_gpt4_turbo`. Prompt bytes, `temperature=1`, `max_tokens=1`, `logprobs=true`, `top_logprobs=5`, and the soft `m`/`M` parser are unchanged. Adaptations are model name, environment-backed client config, and `enable_thinking=false` for every call. Output order is randomized using AlpacaEval's unchanged default seed 0. |
| Endpoint preflight | Phase 2 used the required temperature 0 / max_tokens 5 check. HTTP 200, populated top logprobs, and no reasoning content. Detailed reasoning-token usage is absent; no positive reasoning-token count was exposed. This differs from claiming the endpoint explicitly reported zero. |
| Rejected parameters | None of the Phase 2 or judging request parameters was rejected. No annotator fallback was used. |
| Credential mechanism | Installed `alpaca_eval.utils.get_all_clients` imports the configured `client_class`. `judge_client.DashScopeClient` resolves environment-variable names from YAML; it reads key and base URL only at runtime. No key is written to configuration, telemetry, or reports. |
| Separate judge environment | `aeval` has AlpacaEval 0.6.6 and OpenAI SDK 3.35.1. Setuptools was pinned to 80.9.0 because newer releases remove `pkg_resources`, required by AlpacaEval. TPO retains OpenAI 2.54.0 and its existing packages. Environment versions are saved separately. |
| Length-control estimator | Standard AlpacaEval `length_controlled_v1`, including its original GPT-4-derived gamed-baseline calibration. The local evaluation wrapper sets each annotation's DataFrame index to its original 805-prompt slice ID, avoiding accidental use of positions 0–99. Calibration provenance is in `judge_config/calibration_provenance.json`. Qwen judging and the 100-prompt slice limit interpretation of LC values. |
| Uncertainty | Paired bootstrap resamples prompts 10,000 times, seed 42, with percentile 95% CIs. WR differences compare per-example weighted preferences against the same GPT-4 reference, not direct pairwise judgments of the two candidate stages. LC SEs condition on fitted GLMs and omit refitting uncertainty. Exceeding one SE is not a 95% significance claim. |
| Cached judging | Identical instruction/response pairs reuse AlpacaEval's cache, including the five-example smoke test. All stages have 100 judged examples; 398 new full-stage requests and 5 smoke requests were needed. Token usage is recorded, with no unsupported monetary-cost estimate. |
| Determinism | Generation seeds and original data are fixed, but GPU concurrency and an unversioned remote judge alias can still prevent bit-for-bit reproduction in future runs. The original outputs and cached annotations remain the authoritative results. |
