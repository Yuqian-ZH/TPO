# Task 2 decision log

Decisions outside the plan, or ones that needed the user's confirmation, in chronological order. The "Limitations" section of the README draws on this file.

## Stage 2 implementation choices (2026-10-22)

1. **The upper bound of the load MTZ variables is the total demand, not Q.** `u[i] ∈ [q_i, Σq]`, and the big-M of `mtz[i,j]` is also Σq. This way the subtour elimination constraints do not imply capacity; capacity is expressed only by `cap[k]`, so an IIS lands on `cap[k]`.
2. **Both vehicles must be used:** `depot_out[k]: Σ_j x[k,0,j] = 1`. The enumerator likewise enumerates only two non-empty routes.
3. **Four additional objective terms:** `balance = |L1−L2|`, `makespan = max(L1,L2)`, `load_balance = |W1−W2|`, `sum_arrival = Σ A[i]`, default weight 0, weights must be ≥ 0; `set_objective_weight` has "set" semantics, so if a term is given twice the last value wins.
4. **Quantities bounded only from below accept only `<=` soft constraints:** `A[i]`, `balance`, `makespan`, `load_balance`, `sum_arrival`. A `>=` would be bypassed by the solver raising the variable's value.
5. **ObjVal tolerance:** Gurobi's default integrality tolerance acts on the big-M rows, so ObjVal can differ from the value recomputed from the routes by about 4e-5. Every reported value is recomputed from the routes; the tests require the recomputed value to equal the enumerated value exactly, with an ObjVal tolerance of 1e-3.
6. Cross-checking fixed one bug in the enumerator (`set_objective_weight` was accumulated). After the fix: 77 pytest tests, and 0 mismatches over 1,000 random modification/query pairs.

## Stage 3 case design (2026-10-23, pending confirmation at pause point 2)

1. **Weight complaints can use only `balance` and `load_balance`.** On this instance `makespan` can only go down to 207 (now 211) and `sum_arrival` to 573 (now 588), so changing their weights leaves almost no room for improvement and no credible complaint. The weight of `balance` must be < 1: at 1 the objective degenerates to 2 × makespan with many tied optima (56); above 1 it rewards lengthening the short route. With weight 0.8 the gap falls from 71 to 46, so T7's threshold is 50 km. With `load_balance` weight 4 the load difference falls from 9 to 3 (+18 km); T8's threshold is 5.
2. **The penalty of a reference modification is chosen so that every optimal plan removes the complaint:** T2's `W[1] ≤ 92` with penalty 10 or 20 still has an optimal plan with load 93, so 30 is used; development case D1's `S[1] ≤ 3` uses 60.
3. **T1's localization ground truth accepts only `L[2]` + add soft constraint.** The complaint names vehicle 2; `makespan` currently equals `L[2]` exactly but means something else, so it does not count.
4. **Ambiguous data case T6:** the complaint gives the value 18 but not the field (demand 11 or coordinates (6, 8) are both possible); the clarification answer says it is the demand. `allowed_data_corrections` is `demand[7]=18`.
5. **Vehicle identity:** solving the reference modifications uses the same single anchor as the counterfactual queries (the lowest-numbered customer outside the routes the modification involves stays on its vehicle). So the answer to "move customer 7 to vehicle 2" has 6 customers switching vehicles: vehicle 1 is defined as the route containing customer 1, and customers 5, 6 and 8 move to vehicle 1 with it. This is a convention, not an error.
6. **Many modifications lead to the same alternative plan** (total distance 368: `[1,7,2,8] / [4,5,3,6]`). This is the structure of the instance: among the 14 groupings that satisfy capacity, it is the second best.
7. All 8 "objective preference" attribution cases fall on 8 different edge-difference sets; the ground truth of both capacity-forced cases is `{cap[1], cap[2]}`, and both `cap` constraints were verified to appear in every IIS (removing either makes the model feasible).

## Stage 4 implementation and development debugging (2026-10-23, development cases only)

2. **The explanation prompt was revised twice** (looking only at development cases):
   - In the first version the field names `edges_added` / `edges_removed` were ambiguous, and the LLM described the alternative plan's edges as the current plan's (D1, D3, D5). 3. **How numbers are checked:** a number in an explanation is compared with the numbers in the JSON at the precision it is written (2.02 matches 2.0213), ignoring sign (direction is expressed in words).

## task2_v2 after the audit (2026-10-27)

After an external audit (F1 to F10), the user asked to "re-run Task 2 onwards according to the audit". The rules are unchanged: frozen files and `results/` are never touched, fixes go into a new version in `v2/` with results in `results_v2/`, and old and new are reported side by side. `v2/` matches none of the wildcards of the Task 3 and Task 4 freeze lists, and the v1 protocol checks of both still pass (verified).

1. **F1, attribution v2** (`v2/attribution.py`): v1 solved the model with the decision forbidden without an anchor, then converted the alternative plan to canonical form (the route containing customer 1 becomes vehicle 1, routes reversed), which changes the objective under soft constraints that depend on vehicle number or direction, such as `L[2] ≤ 180` or `A[i]`. Reproduced in agreement with the audit: among the 343 iteration 2 and 3 attributions of Task 3 v1, 18 numbers were wrong, concentrated in 2 trials, and 15 "cheaper when forbidden" cases were reported as objective preference. v2 adds the anchor, does not renumber, reverses a route only when the objective is unchanged, and checks that the alternative's objective equals the solver's.
2. **The anchor choice was changed twice (both before the v2 protocol was frozen, using non-test data and LLM-free evaluation):**
   - The first version took, as is Task 2's convention, "the lowest customer involved in neither the decision nor the modifications". On the T2 reference-fix plan (`W[1] ≤ 92`, 390) this anchor (customer 2 stays on vehicle 2) allows a plan with swapped vehicle numbers at only 380, so all 25 decisions were judged "cheaper when forbidden". The reason: once a constraint depends on the vehicle number, the anchor is no longer just a labelling convention; it changes the feasible set. Change: try anchors in the same order and take **the first anchor under which the current plan itself is optimal**, so that the current and the alternative plan are compared on the same feasible set (for the T2 reference plan that is customer 3, exactly the anchor used when it was solved). Only when no such anchor exists is the current plan truly not optimal, and the conclusion is then recorded as `cheaper_without`.
   - The second version exposed another problem on Task 5's constructed scenario (changing the capacity): a capacity change counts every customer as "involved", the anchor falls back to customer 1, and customer 1 is one side of the attributed decision `SEP(1,3)`; with that anchor the IIS contained only `cap[1]`. Change: the decision's own customers go last among the anchor candidates; when infeasible, the anchor is dropped before computing the IIS (feasibility does not depend on vehicle numbers), as in v1, and enumeration confirms both capacity constraints are in every IIS.
3. **Results (the LLM-free part, `results_v2/task2_v2_results.md`):** the 10 test cases are still 10/10, P = R = 1. A new evaluation of "plans under soft constraints": the 10 reference-fix plans plus 14 Task 3 loop states, 912 decisions in all, checked by enumeration; v1's alternative objective was wrong in 149/885 (largest error 46,500), v2 right in 885/885; edge sets right in 885/885 in both versions (edges do not depend on vehicle numbers); v2's claim that "the current plan is optimal under the chosen anchor" holds in 912/912, checked by enumeration.
4. **F4, timing:** the same queries with three methods (the frozen local rule, Task 3's v2 escalation rule, the full solve), each timed with a resident model and with a newly built model per query. Building the model takes only 1 to 2 ms on this 9-node instance, so after a fair comparison the conclusion barely changes (main queries, median: local 12.8 ms against full 35.6 ms, both on the resident model). The v2 escalation rule fixes T1 (stuck at L0) but does nothing for the 14 supplementary MOVE/FIX_ARC queries that stop at L1 (those are hard constraints with no soft-constraint violation); reported as is.
5. **F5, localization v2** (`v2/localization.py`): agreement is now counted on "target, direction, threshold, corrected value"; the modification type is the majority among the agreeing samples and is no longer a reason to ask; under low confidence the question addresses the first point of disagreement in words the user can answer (no internal IDs such as `W[1]`). Recomputed on v1's saved samples: Task 2's own 60 verdicts are identical to v1's; T7, which the v1 rule stopped in Task 4, becomes high confidence in both localizations (`balance ≤ 50`, soft constraint).
6. Freeze: `v2/protocol_v2.json` (28 file hashes) was written before any LLM call; the LLM part of `v2/evaluate.py` refuses to run if a hash differs, and each part's results are written once. Seeds follow Task 2's derivation with the component names `explain_v2` and `localize_v2`, so all samples are new.
7. **Results of the LLM part (2026-10-27, all 330 requests succeeded at the first attempt, every response from `qwen3.8-max`):** explanation 30/30 passed the checks at once; three new localization samples give exactly v1's metrics (first pass 90%, all 7 high-confidence cases right every time, the 3 vague complaints asked every time, 100% after clarification, modification type 100%). All 9 questions were written by the LLM itself (the samples agreed on the meaning but flagged "ambiguous"), and all are questions a user can answer. The v2 rule has no side effect on Task 2's own cases; what it really changes is the T7 kind of case, "same meaning, different modification type".
8. **Independent review after the run:** a separate review agent read only the v2 code and reported an anchor tolerance that was too wide (0.1% relative tolerance, which misjudges with fractional weights), attribution still being done when the current plan is overloaded, localization not checking that the modification type is legal, and thresholds counted for agreement even for forbid/require; all reproduced with constructed inputs. Checked item by item: across the 2,677 attributions that actually entered Task 3 and Task 4 v2 prompts and the 912 of this evaluation, the anchor judgement and conclusion are all right under an exact tolerance; every high-confidence critique has a legal modification type, so the reported results are unaffected. The frozen v2 files are not changed and the fixes are a separate version; the unfrozen `v2/report.py` had one counting hole fixed (missing values counted as correct), and its re-run output is word for word the same. README 8.4 states this.

## task2_v2.1: fixes from the post-audit review (2026-10-27)

Done after the user confirmed the fixes. Same rules as v2: the frozen `v2/` and `results_v2/` are untouched, the fixes go into a new package `v21/` that replaces only the faulty functions and imports the rest from v2. `v21/` and `tests/test_v21.py` match none of the wildcards of any existing freeze list (deliberately not named `v2_1` or `test_v2_1.py`; the latter would match v2's `tests/test_v2_*.py`).

1. **Anchors use an exact comparison:** under an anchor, the current plan counts as optimal only if the solver's plan, with its objective computed by `canon.objective`, is not lower than the current plan's (tolerance 1e-6). The model's MIPGap is 0, so the solver's plan is optimal. In the reviewer's example v2 judged 16 of 38 decisions `cheaper_without`; v2.1 judges none, and all 38 were checked by enumeration.
2. **No attribution when the current plan is overloaded:** the conclusion is recorded as `current_plan_infeasible`, the overloaded vehicles are listed, no alternative is solved, and the explanation uses a template without calling the LLM. An incomplete plan (missing or repeated customers) raises an error, because that is a wrong input rather than "inconsistent with the model data".
3. **The modification type must be one the target allows:** among the agreeing samples, the majority is taken only over the allowed types; ties still go by sample order. If none is allowed, the target's first allowed type is used (`modify_data` for data targets, soft constraint for the four objective terms, soft constraint otherwise). The type is still never a reason to ask.
4. **Whether a limit applies depends on target and direction:** data targets look at the corrected value; other targets look at the threshold for decrease/increase; forbid/require look at neither. Judging by direction alone (correct looks at the corrected value) was also considered, but samples such as "customer 4 needs more: 13" are described with direction increase, and judging by direction would drop the 13. Among the 970 recorded valid samples, data targets are all correct with a corrected value, paired targets never fill a limit for forbid/require, and quantity targets are all decrease, so the two rules make no difference to existing results. The inapplicable value in a critique is the most common one among the agreeing samples, which is exactly what v2 gives when confident.
5. **LLM-free recomputation after the freeze:** after `v21/protocol_v21.json` was frozen (35 hashes, including all of v2's frozen files), `python -m v21.recheck` was run: on the 10 test cases, the inputs of 30 explanations, the decisions of 912 soft-constraint plans and 120 sets of localization samples, v2.1 equals v2 field by field. Task 3 and Task 4 each checked their own records, also without differences.
6. **A pitfall met while checking:** the first Task 3 recomputation produced 22 cases of "different objective term name" (`soft:tpo_1_1` in the record, `soft:balance` in the recomputation) with identical values. The loop numbers soft constraints when committing (`tpo_<iteration>_<index>`), the trial record stores the modifications without the number, and the recomputation had not restored it. Restored by the same rule, the count is 0. This is not a v2.1 difference: v2 gives `soft:balance` on the same unnumbered input too.
7. **The other side of the conclusion:** not a single result changed, which means the existing evaluation data never reached these code paths; the only evidence that the fixes are correct is the constructed examples in `tests/test_v21.py`.

## Third version of the test cases, task2_v3 (2026-10-27)

The user pointed out that the Task 3 ablation, as designed, could not tell the mechanisms apart, and asked for a redesign against the task requirements. The task requires Task 2 and Task 3 to use the same 10 test cases, so the new design starts from Task 2's cases. The overall design is `DESIGN_V3.md` at the project root.

1. **Cases are built by stratum:** 2 control, 3 ambiguous, 5 side condition, and 10 development cases by the same recipe. Every requirement of the user is written as a condition (`v3/conditions.py`) that appears in the complaint or in the user's explanation; there is no longer a hidden threshold given only to C.
2. **Every property is asserted by enumeration at build time** (`v3/cases.py`). Two details were handled during construction: (1) the commit solve fixes one customer to its original vehicle (the lowest-numbered customer not involved in the modifications; customer 1 when every customer is involved); the only feasible swap in one early development case had to move customer 1, which no modification could reach, so it was replaced; (2) on direction ties the commit takes the canonical direction, and the builder does the same, otherwise whether a misreading solves the complaint would depend on the direction. The "shortest compliant plan" excludes plans where the two vehicles swap whole routes (the system can never produce them).
3. **A coverage gap found after the freeze:** the 10 attributions of the test set were all objective preference and the 10 counterfactuals all feasible, so the IIS path and the infeasible case that the task asks for were not tested. No LLM had been called yet and Task 3 was not frozen, so only 4 question fields of U1, U7 and U9 were changed ("customers 1 and 3 on different vehicles" is the only capacity-forced decision in these plans) and the cases were frozen again. The first freeze's files and deterministic results stayed in a scratch directory and never entered the repository.
4. **Evaluation results:** attribution 10/10, P = R = 1; explanation 30/30; full re-solve agrees with enumeration everywhere; the local probe Task 3 uses agrees on the objective 25/28 and on the change set 20/28 (worse than on the v1 test set, since the new queries involve more vehicle switches); localization 90% at the first pass, every high-confidence case right, 100% after clarification. Two side-condition complaints were asked every time (one sentence with two conditions, and the samples disagree on the target).
