# Task 4 design decisions and deviations

In chronological order. References such as "plan 3.7" are to the task's execution plan, which is not part of this submission.

## 1. Reuse Task 3's loop core without changing it (plan 3.7)

Task 3's `tpo/loop.py` is frozen (`Task 3/task3/protocol.json` records the hashes of 49 files), and changing it would invalidate Task 3's acceptance. Task 4 imports it read-only and uses three seams to replace "the simulated user decides on the spot" with "a real user replies with the next HTTP request":

1. `DeferredUser`: `Trial.step()` touches the user only through `verdict`, `feedback` and `illegal_data_mods`. In the service the verdict is always "awaiting reply"; `resolved` and `label_swap_resolved` are called only by the tie diagnostic and on "resolved", which never happen in the service, so calling them raises an assertion.
2. When the user replies "not resolved", the placeholder text in the last entry of `trial.history` is replaced by the user's own words (Task 3's fixed template if empty), and the `Trial` is rebuilt from storage for the next iteration.
3. `ServiceTrial.blocks()`: when accepted modifications exist, a note is added before the "modifications currently in force" block. Without them the prompt is word for word Task 3's.

**Verification:** `tests/test_equivalence.py` uses the same synthetic case and the same stub script over 8 main configurations × 6 situations (fixed at iteration 1; fixed after a new plan; fixed after a rejection and an unchanged plan; never fixed; fixed after clarification; still unclear after clarification) and compares "Task 3's `SimulatedUser` driving the service over HTTP" with "calling Task 3's `run_trial` directly": the state, full prompt text, candidates, selection, committed modifications, new plan and final outcome of every iteration are identical; 48 tests pass. It also asserts which branch each situation actually took (how each iteration was triggered).

## 2. A single engine thread (plan 3.1, 3.6)

Task 2's `model.py` shares one Gurobi environment per process, and Task 3's `counterfactual_v2` caches a resident model; neither is thread-safe. All work that touches the solver or the LLM (including solving the initial plan when a session is created) runs sequentially on one thread; HTTP threads only validate, store, enqueue and wait. `tests/test_worker.py` asserts that when 3 sessions submit concurrently, every component call runs on the same engine thread. The cost is that requests from several sessions queue up; the README lists this under limitations.

## 3. Only modifications the user accepts stay in the model (plan 3.3)

When the final state is not `resolved` (3 iterations used up, user `stop`, processing failed, service restarted while processing), the session returns to the plan the complaint was made against and the complaint's modifications are void; all of it stays in the logs. On acceptance the modifications are merged into the session's `accepted_modifications`, and soft-constraint IDs are rewritten as `acc<n>_<k>` (otherwise every complaint would produce `tpo_1_1`).

## 4. No new plan, no question to the user (plan 3.7)

When every candidate of an iteration is invalid, the modified model is infeasible, or the new plan is identical to the input plan, the service runs the next iteration directly, with the user's previous reply to that plan as the feedback text (Task 3's `FEEDBACK_UNRESOLVED` template at iteration 1). The simulated user's verdict depends only on the plan, so this matches Task 3's behaviour (the equivalence test's "fixed after a rejection and an unchanged plan" situation covers two automatic continuations in a row).

## 5. An unavailable LLM must not pass as a normal result (plan 3.6)

Task 2's `LLMClient` does not raise on network errors or 403; it returns an empty result (Task 3 once got 403 for a whole batch when the account lost permission). Left alone, localization would turn into "low confidence" and ask the user, and proposals would turn into "invalid". The service wraps the client in `CountingLLM`: if any request of a job gets no reply, the job's result is discarded and the feedback is marked `failed` (`llm_unavailable`). `tests/test_worker.py` verifies with the real Task 2 localization component that when none of the 5 samples gets a reply the result is `failed`, not `needs_clarification`.

## 6. Default configuration `A0B0C1` (plan 3.10)

Based on Task 3's formal experiment: the 4 configurations with C on all converge 100% at iteration 1, and `A0B0C1` uses about 1.8k tokens per trial; A has no measurable effect, and B helps only with C off. Each session may choose any of the 8 main configurations; S1 and S2 are experimental controls and are not offered.

## 7. Deviations from the plan

1. **`httpx` was not in the environment.** Section 2 of the plan said "depends on the existing `httpx`", which was wrong (`openai 3.36` depends on `httpx2`). `TestClient` and the end-to-end client both need it; a dry run confirmed that only `httpx` and `httpcore` would be added, they were installed, and recorded in `env.json`.
2. **An extra `feedback_service/service.py`:** orchestration unrelated to HTTP (storage, state machine, jobs, replies, views) lives here, and `app.py` only maps routes, so tests can exercise concurrency without HTTP.
3. **The development smoke test also ran `A1B1C1` and one restart** (plan 5.2 mentioned only `A0B0C1`): the test-case end-to-end run uses `A1B1C1`, so the attribution, probe and selector path should first run once with the real LLM on development cases; the restart was also rehearsed on development cases first.

## 8. Problems found in testing

- The first version of `test_equivalence.py` had a wrong expectation for "never fixed": I assumed iteration 3 was an automatic continuation, but iteration 2 had changed the plan back to the initial plan (a new plan relative to iteration 1), so iteration 3 was triggered by the user's reply, its plan was unchanged and the budget was used up, so it ended. The service behaved correctly (both paths agree); the test expectation was fixed.
- The first version of `test_task2_components.py` asserted that the evidence contained only `S[2]`; Task 2's evidence gives both vehicles' values for comparison, so the test now checks only `S[2]`.

## 9. End-to-end results on the test cases, and T7 (13:08 to 13:15, run once after the freeze)

- `A0B0C1` solved 10/10 at iteration 1 (T2, T6 and T8 after clarification); `A1B1C1` 9/10, with T7 ending in `stopped_low_confidence`. All 181 requests succeeded, about 450k tokens; the service was restarted while T5 awaited a reply, and the state was the same before and after. All 10 acceptance items pass.
- **T7 is not a service problem:** the localization prompt the service sent is word for word the T7 request in Task 3's logs, with only the seed different (the service derives its seed from the feedback ID); the second localization did carry the clarification answer, with different seeds again. All 5 samples target `balance` (threshold 50) and none is ambiguous, but the modification type splits 3 soft constraint to 2 objective weight; Task 2's frozen rule needs at least 4/5 agreement on (target, modification type), so it judged low confidence and asked Task 2's generic question; the user's answer was about the target (where there was no disagreement), the second round was again 3:2, and by the rule it stopped without passing to TPO.
- **Conclusion:** the service handled low confidence as the task requires, but this exposes a design flaw in Task 2's confidence rule: it counts a disagreement the user cannot resolve (the modification type is an internal choice of the system), so no clarifying question can remove it. A better rule would judge confidence by target agreement only and leave the modification type to TPO or the counterfactual probe to compare. Task 2's localization component is frozen and the test cases run only once, so nothing was changed or re-run; README section 7 states this, and it serves as material for Task 5 point 2.
- All other low-confidence localizations are complaints designed to be vague: 9 of Task 3's 30 (T2, T6, T8), and here, excluding T7, 10 of 29 (T2, T6, T8, D1, D4).

## 10. Numbers corrected while checking the README

After checking each against the raw data, 5 places were corrected: the run time (6 min 25 s, not 6.5 minutes), the reply latency (4 to 10 ms, not 6 ms), the duration range in the limitations section (9 to 37 s), the count of "other low-confidence localizations" (first written as "another 30", then mistakenly as "9 of 29", actually 10 of 29), and the fact that T7 was asked Task 2's generic question, not the service's own.

## 11. task4_v2 after the audit (2026-10-27)

1. **F2 holds** (`_refine` in `feedback_service/service.py`): whether there is "something new to show the user" looked only at whether the routes changed. When the user says "customer 4's order is 13, not 12", the optimal routes do not change after the demand change (vehicle 1 is exactly at 100/100), so the service did not show anything, continued automatically, closed the complaint as `not_converged` after 3 iterations and withdrew the modification: a correct correction was lost. A test with a fake LLM reproduces this (the first test in `tests/test_v2_service.py`, kept as a regression record).
2. **Fix** (`feedback_service_v2/service.py`): judge whether the state changed by routes and effective data together. Changed routes work as before; unchanged routes with changed data produce a `data_corrected` plan version whose view says "your correction is in effect; with the corrected data the current routes are still optimal, please confirm", and after the user confirms the correction stays in the session; if neither routes nor data changed (only an ineffective soft constraint or weight), it continues directly as in v1 without bothering the user. Only `_refine` is overridden; everything else is inherited from v1, and the v1 files and `service_freeze.json` are untouched.
3. **Components switched to v2:** through Task 3's `tpo_v2` adapter, Task 2's task2_v2 attribution (F1) and localization rule (F5, which removes T7's stop) are used. At start-up both of Task 3's protocols are checked (v1 49 files, v2 58 files).
4. **Re-run plan:** development cases once (not frozen) → freeze `service_freeze_v2.json` → 20 test-case sessions (`A0B0C1` and `A1B1C1`, with a restart while `A0B0C1`'s fifth case awaits a reply) → the audit scenario `scenarios/audit_cases.json` (demand 12 corrected to 13) on both v2 and the frozen v1 service with two configurations each, comparing whether the correction is kept. The audit scenario was written after the audit and is reported separately, not merged into the test cases.
5. **Results (2026-10-27 10:52 to 11:05, all 256 requests successful at the first attempt, every response from `qwen3.8-max`):** the development cases were solved 5/5 at iteration 1 before `service_freeze_v2.json` (20 hashes) was frozen. All 20 test-case sessions were solved at iteration 1, and T7 no longer stops under the fully enabled configuration; the state was the same before and after the restart; all 20 iteration records have the five fields, and the two feasibility checks agree; no credentials in the results folder. Audit scenario: under v2 both configurations show the `data_corrected` plan at iteration 1, the user confirms, the correction is kept, plan 351 km; on the frozen v1 service `A0B0C1` committed the correct correction in all 3 iterations but never showed it, and finally withdrew it; `A1B1C1`, told "not resolved", added an unrequested `balance <= 20`, the user accepted a 398 km plan, and this extra constraint would stay in the session.
6. **This run's latency cannot be compared with v1's:** while the test cases ran, a Time Machine backup was running on the machine (`backupd` at about 80% CPU, `diskimagesiod`), and the editor's C++ extension `cpptools` was indexing (about 100%), with a 15-minute load of about 18 (12 cores). In the `A1B1C1` segment even the commit solve went from 0.055 s in the first half of the same run to 0.42 s. Functional results are unaffected; the frozen test cases are not re-run to get nicer timings. The overhead of v2 attribution itself was measured separately on an idle machine: 0.077 s per decision against 0.051 s for v1 (Task 3 batch medians 0.085 against 0.065 s), and the README says so.
7. **Independent review after the run:** v2's rule treats any data change as "your correction is in effect". When data reverts after the user rejects a plan, or the LLM changes data on its own while the routes stay the same, the message is wrong. In this run only the audit scenario triggered it, twice, both for corrections the user asked for and with no rejection, so the results are unaffected. The fix (compare with every state the user has seen in this complaint, and list the specific data changes in the message) is a separate version, without changing the frozen service. README section 10 states this.

## 12. task4_v2.1 after the review (2026-10-27, check only, no end-to-end re-run)

1. **Fix** (`feedback_service_v21/service.py`): compare this iteration's (routes, effective data) with every state the user has already seen in this complaint (the plan complained about and every plan shown since), and show it only if unseen; a seen state continues directly as in v1. Seen states are stored with the trial state. If a shown plan's data differs from the data at the start of the iteration, the message lists each change ("customer 4's order 12 -> 13") and asks the user to check, instead of saying "your correction is in effect". A plan whose routes and data both changed now carries this message too (v2's did not).
2. **Components** switched to Task 2's v2.1 (through Task 3's `tpo_v21`); at start-up, besides Task 3's two protocols, Task 2's `v21/protocol_v21.json` is also checked.
3. **Tests:** 9 new tests, with v2's wrong behaviour kept as a regression record beside v2.1's: when a correction is lost after a rejection, v2 shows the plan the user complained about again and claims the correction is in effect, while v2.1 keeps iterating and ends `not_converged`; when the user complains that vehicle 2 has too many stops and the LLM changes customer 5's demand instead, v2 says "your correction is in effect", while v2.1 lists the change and asks the user to check.
4. **Check:** after freezing `service_freeze_v21.json`, `recheck_v21.py` replays every complaint of v2's three runs (development cases, test cases, audit scenario) in iteration order under v2.1's rules, and recomputes the components on the recorded states and samples: 27 state judgements, 175 attributions and 35 localization sample sets, all identical to v2. The replay stops at the first difference (what follows depends on that judgement); there was none, so the whole replay is exact.
5. **The only visible difference:** among the 27 plans shown, those with a data message went from 2 to 7. The extra 5 are plans with changed routes (T5 and T6 under two configurations each, plus one development case), and every change is a number the user stated in the complaint (customer 4 to 20, customer 7 to 18, customer 2 to 30). Checked one by one: v2's runs have no case of the LLM changing data on its own; the simulated user does not read messages, so its answers would not change.
6. **No end-to-end re-run:** the service's behaviour differs only in the state judgement and the message text, and the replay has proved every judgement identical; spending LLM calls on a re-run would only produce another batch of random outputs (Task 3 DECISIONS item 8: fixed seeds do not reproduce).

## 13. task4_v3, the service for the redesigned experiment (2026-10-27)

1. **Why change the service:** the task requires Task 3 to use Task 4's loop. The third version of Task 3 starts every iteration from the plan complained about (the pilot found that starting from the previous, rejected plan breaks the reference of conditions such as "at most two customers switch vehicles" and "vehicle 1's route cannot change"), so the service must follow, or the two would not run the same loop.
2. **Change** (`feedback_service_v3/`): `EngineV3.trial()` restores only the history, not the previous iteration's plan and modifications; within one refinement, the trial is also reset to the original plan before an automatic continuation. The plan shown to the user and its modifications are still recorded in the complaint record for replies and acceptance. The state-change rule is v2.1's (compare with every state the user has seen in this complaint).
3. **Equivalence:** 26 new tests show that over 8 configurations × 3 development-case scenarios, the service's prompts, candidates, selections, commits and plans in every iteration are word for word those of Task 3 v3's `run_trial`. One difference remains, fixed by a test and stated in the README: when an iteration's result has already been seen by the user, the service does not show it and continues with the user's previous words, whereas Task 3's simulated user comments on it; when every iteration produces a new plan the two are identical.
4. **Run:** after freezing `service_freeze_v3.json`, two configurations on the new 10 test cases: `A0B0C1` 10/10, `A1B1C1` 9/10 (U10 unresolved, exactly the case where Task 3 found A harmful). Task 3's batch had finished before this; but while the `A1B1C1` segment ran I ran the test suites of Tasks 2, 3 and 5 (about two minutes), so this segment's timings may be high; the README states this.

## 14. The service follows Task 3 v3.1: show the session's own modifications (2026-10-27)

1. **Why change it:** Task 3 v3.1 lists the modifications already in the session in the prompt. The service listed only modifications the user had accepted in earlier complaints, not those the session was created with; they were in the solver's model but not in the prompt. So that Task 3 uses Task 4's loop, the service follows.
2. **Change** (`feedback_service_v31/`): `ServiceTrialV31` first lists the session's own modifications (calling the same Task 3 function), then the accepted modifications, then "modifications currently in force". When neither exists, the prompt is word for word task4_v3's.
3. **Equivalence:** 36 new tests show the service matches Task 3 v3.1's `run_trial` word for word over 8 configurations × 4 development-case scenarios (2 of them with session modifications).
4. **Run:** after Task 3's `protocol_v31.json` was frozen, `service_freeze_v31.json` was frozen and `A1B1C1` ran once on the 10 test cases: 8/10. U9's localization was still uncertain after clarification, and by the rule the service did not pass it to TPO; U10 was not resolved in three iterations. All 118 requests returned normally, and nothing else ran during the run.
